# wm-import-eval

A from-scratch reader for World Machine `.tmd` (`TMDFile2`) save files, plus a
translator that recreates them as bar-editor `.barproj` recipes. Built to answer
one question: **what do real BAR map-makers configure in World Machine that
bar-editor can't yet express?**

Read **[REPORT.md](REPORT.md)** for the findings. This file is just how to run it.

## Run

```bash
# Device-type inventory + WM's own param tooltips/enums for a file
python tmd_model.py <file.tmd>

# Full translation: writes <map>.coverage.json + <map>.barproj
python translate.py <file.tmd> [out_dir]

# Validate a generated recipe against bar-graph's node/port/param schema
python bar_schema.py <map>.barproj

# WM device -> bar node mapping table
python mapping.py
```

Tested against a 6-map corpus in `~/Downloads` (3631 devices, 52 device types):
ATG2, onyx2, BSR, cells, canis_river (Peter Sarkozy) and Aethermoor Creek
(Angelwing). `corpus.py` summarizes all of them at once.

## Files

| File | Role |
|------|------|
| `tmd_parse.py` | The binary format: recursive `WM`-block tree parser |
| `tmd_model.py` | Tree -> device records (type FourCC, name, position, params) |
| `par2_decode.py` | Decode a device's flat `PAR2` blob (older WM, e.g. ATG2) |
| `parmgroup.py` | Decode the newer self-describing `ParmGroup` tree (e.g. Aethermoor) |
| `par2_dump.py` | Annotated byte-level dump of a `PAR2` blob (structure RE) |
| `mapping.py` | WM device FourCC -> bar node, with good/partial/gap status |
| `compare.py` | Per-param WM-vs-bar gap, values aggregated over all instances |
| `corpus.py` | Cross-file summary over every `.tmd` in `~/Downloads` |
| `translate.py` | `.tmd` -> `*.coverage.json` + runnable `*.barproj` |
| `bar_schema.py` | Recipe validator (transcribed from `crates/bar-graph`) |
| `explore.py`, `hexfields.py`, `inventory.py` | Reverse-engineering scratch tools |
| `REPORT.md` | The capability gap analysis (the deliverable) |
| `CHANGES.md` | Gap-closing changes made to the bar-editor source (with verification) |
| `feature-test.barproj` | Recipe exercising every newly added param/node |
| `PARAM_GAPS.md` | Per-parameter WM-vs-bar tables (generated by `compare.py`) |
| `*.coverage.json`, `*.barproj` | Generated per-map outputs |

```bash
python par2_decode.py <file.tmd> <FourCC> [n]   # decode params of the n-th device of a type
python compare.py > PARAM_GAPS.md               # regenerate the per-param gap tables (whole corpus)
python corpus.py                                # cross-file summary of every .tmd in ~/Downloads
```

## Format notes (`TMDFile2`)

- Tree of `b"WM" + name_len:u8 + name + size:u64le + payload` blocks.
- Containers may prefix children with a u32 count or `FourCC+version[+count]`.
- Devices: `DEVICEWORLD > Devices > Device2{ ID, Contents>Device{ basic, id,
  params } }`. `ID` is a 4-char type FourCC; `params` is a `"PAR2"` blob.
- The `PAR2` param blob stores each parameter as a fixed record starting with
  the marker `50 31 07`; the 4-byte value sits at +3 and the param name at +59.
  This holds across device types and both the `WM Device` wrapper format and the
  older inline format (APRL). Param names/counts and float values decode
  reliably (`par2_decode.py`); a few int/enum/bool fields keep their value in a
  side slot and read as raw words. Reliable enough for the gap analysis; a
  lossless importer would need the remaining per-type field offsets.
- Newer WM builds (Aethermoor) drop `PAR2` for a self-describing `ParmGroup`
  tree: `params > ParmGroup > parms > P4FULL{ name, type, val>(float|enum>choice),
  min, max, step }`. Decoded by `parmgroup.py`. The two sample maps use the two
  different families -- the param format varies by WM version.
